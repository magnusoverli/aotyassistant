# Multi-provider search

Included in **0.2.8**, not 0.2.7. The deployed Metallica search response was inspected read-only to reproduce its missing cross-provider IDs; no live catalogue, saved list or speaker was changed to test it.

## Behaviour

- Artist-first MA search and track-only demo search are unchanged. Participants may switch to tracks. MA's library and connected sources remain included; there is no Spotify/Tidal-specific search filter or second catalogue API.
- **Identity groups** (`matchKind: "identity"`) use matching MA provider-instance/item mappings or valid MusicBrainz artist IDs. Releases require a MusicBrainz **release** ID or mapping; release-group IDs/barcodes alone are not enough. Tracks require a recording ID, ISRC or mapping, with exact normalized title/version/artist/context guards. Names alone never establish identity. Case/Unicode normalization is not fuzzy matching; punctuation, edition words, album appearance, conflicting known years, duration, disc/track positions, explicit flags and conflicting IDs are preserved. Complete-link grouping prevents an ambiguous mapping bridge from merging contradictory identities.
- **Metadata display groups** (`matchKind: "metadata"`) address the deployed ID-less Spotify/Tidal shape: each result has `external_ids: []` and only its own provider mapping. Same-name artist matches share one row labeled **Same-name matches · choose a source to browse**; they are not declared to be the same artist. Album/track display groups additionally require matching title/version/artist/context and no known conflicts; tracks require meaningful matching duration/album context. No fuzzy matching is used. Known conflicting identities stay separate. When an unknown result could fit multiple conflicting known artists/editions, it is not arbitrarily assigned to either; compatible unknown results share their own display row. Same-provider ambiguity is retained or offered as numbered original choices, never silently paired away.
- Source names come from public MA provider domains, not account names/instance IDs. Every group retains every exact original source choice; multiple entries for the same service receive stable option numbers. Display grouping neither changes canonical equality nor deduplicates saved recordings. Metadata group references are display-only and server-side rejected for browse/save/play; selecting an exact source is mandatory. No automatic union or representative-source browse is permitted for an unverified group.
- Identity-verified artist and album groups default to **All listed sources**. Browsing reads each known source and unions the results, so choosing a representative Spotify artist cannot hide Tidal-only albums. A verified multi-source union is never downgraded into a metadata bucket when an unidentified same-name neighbour appears. Metadata groups instead require separate, explicit catalogue browsing; all catalogues remain selectable, including provider-exclusive albums and sources beyond the automatic fanout limit.
- Track groups have **no default selection**. Choose an exact source to enable Add/Play. Its availability and metadata apply; an unavailable Spotify result does not switch to Tidal. Group references are rejected server-side for both capture and playback. Source variants retain participant/room/catalogue-bound encrypted references and the existing exact URI/provider/item/version recheck, durable saved descriptors, revocation and turn/reveal rules. Saved entries remain separate by exact recording identity; no list migration/deduplication or auto-play is performed.
- Library rows expand MA's explicit mappings to source choices. Mapping-only references use MA's documented `<provider>://<kind>/<item_id>` URI format and must pass the same strict exact-resolution guard. If a deployment rewrites instance identity/URI/version, the selection fails explicitly rather than weakening that guard or substituting another source. A legacy library-URI saved entry without an exact source must be reselected; it is retained, never rebound or deleted.

## Errors and resource bounds

MA global `music/search` can suppress individual provider failures and exposes no reliable per-source completion status in the supported response. Every MA search API response marks coverage as unconfirmed. The UI keeps the general caveat in **Sources and matching**, announces unconfirmed coverage briefly, and explicitly qualifies empty results rather than repeating a warning banner on successful searches. Actual partial browse errors remain visible. An HTTP/auth/shape failure remains an error; it never falls back to demo or becomes an empty success. We do not claim that an empty search proves all catalogues are empty. Adding per-source health guarantees would require a verified upstream completion/error contract, not speculative requests.

For grouped browse, failed source requests are named in an incomplete-results notice, even if the successful sources return zero items. If every attempted source fails, the request fails and the previous choices remain available for retry. Upstream may itself suppress errors inside a provider listing; the app cannot reconstruct those omissions.

Search makes one MA request (`limit: 20`); at most 500 raw search items are accepted, grouped **before** any display reduction (the old early slice is removed). Each item accepts at most 100 explicit mappings/external IDs; at most 1,000 selectable variants are emitted per response. Artist/album browsing makes at most eight requests, two concurrently, with the existing eight-second per-request deadline and 2 MiB response cap. Each listing accepts 500 items and a union accepts 2,000 raw items; oversized results fail explicitly rather than silently dropping a provider. A fanout-cap notice directs users to source-specific browsing, and large album listings warn about possible upstream truncation. Exact references remain capped at 5,000; at most 1,000 browse groups retain at most 5,000 source-reference slots in total, not copies of upstream metadata. Expired/evicted sources require a fresh search. The existing twelve-hour expiry and credential/runtime revocation remain. No recursive source search, matching hydration, automatic retries, or playback writes are introduced.

Artist artwork is no longer cached by provider/name alone: that could attach one same-named artist's portrait to another. Only supplied item artwork and exact parent references are reused; missing portraits use the normal placeholder.

## Verification

Synthetic unit/integration and browser fixtures cover both identity grouping and the deployed ID-less search shape for Metallica, Iron Maiden, Megadeth and Slayer, source-required metadata browsing, known/ambiguous same-name artists, provider-only albums, release/recording distinctions, partial/full/empty source failure, fanout/concurrency bounds, source availability, opaque nested references, revocation, exact saved capture and rejection of substitutes. Mapping-only URI/provider rewriting still fails closed; no alias guard was weakened. The full existing lifecycle/privacy/browser suite remains the regression gate. No real speaker validation or real-catalogue completeness claim follows from these fixtures.

Before publishing 0.2.8, the built client also read the deployed catalogue: Metallica produced **one metadata display row** with Spotify and Tidal choices; source-specific album reads returned **23 Spotify rows and 170 Tidal rows**. Only `music/search` and `music/artists/artist_albums` were called. No participant, list, integration or speaker mutation was issued; these observations do not establish catalogue completeness.
