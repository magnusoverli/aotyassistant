## Host setup implementation

Application addressing now has [automatic MA-verified media suggestions and UI-configured guest links](application-addressing.md), with a no-audio diagnostic, safe local setup recovery, manual override verification and persistent per-installation origins. It does not register a custom provider or alter host networking.

Use `/host/settings` to save the URL/token and select a speaker/group. Opening/reloading settings and saving a connection automatically discover speakers through a read-only check; there is no separate manual check button. Saving a destination refreshes inventory and validates its queue. Discovery runs outside the playback command lane, with revision and ownership checks before a destination is committed. Configuration lives in the add-on/container’s own data directory. Tokens are write-only at the API boundary; blank means keep only when the origin is unchanged. Browser/public/participant session serializers do not include connection credentials. Host access remains deliberately open, so network restrictions are essential.

The **Active speaker** dropdown lists only currently available entries from a fresh successful discovery report. Selection shows a pending state, then becomes active after backend inventory/queue validation and persistence. Empty and all-offline inventories show an explicit no-available-speakers state with **Refresh speakers** for read-only rediscovery. Unavailable and unconfirmed outputs are distinct from ready outputs; remembered configuration alone is not readiness. Discovery retains the routing preference and does not select a replacement automatically.

One shared server-side monitor subscribes to the existing authenticated Music Assistant event connection, including player additions/removals and availability/name changes even before a speaker is selected. Event hints coalesce for 250 ms before read-only inventory/queue checks; ordinary queue progress and volume updates do not cause inventory scans. A 15-second polling fallback recovers missed events; checks expire after 45 seconds. Settings receives sanitized live snapshots, and host/participant controls show the same output name and health. Status updates neither change the persisted routing revision nor invalidate private browsing. Restart rechecks the remembered speaker before showing it ready; lost availability preserves ownership for Stop/recovery, and restored connectivity cannot clear a recovery requirement or start music.

The client reads unauthenticated `/info` and uses bearer authentication on `/api` and same-origin image-proxy reads. Explicit read-command allowlists cover inventory, queue validation, search, artist albums, album tracks, exact URI lookup, and `players/get`; guarded mutations add only documented queue settings, play/pause/resume/stop, and destination volume commands. No arbitrary command proxy is exposed. Successful HTTP `/api` responses are **the command result itself**, not the WebSocket result envelope. Source URIs and queue payloads remain backend-only. The active queue is resolved per operation rather than assuming the speaker/group and queue IDs match.

## Participant catalogue search

The deployment's `/api-docs/commands.json` documents `music/search` with required `search_query`, optional `media_types`, `limit`, and `providers`, requiring `library.read`. The request uses `media_types: ["track"]`, `limit: 20`, and omits `providers`, so Music Assistant searches its library and all available sources. Adding Tidal or another supported provider in Music Assistant needs no app code change. Some providers search only indexed library content; availability and provider capabilities still apply.

All joined participants may search/browse immediately, including before their first turn. One persistent room exists automatically; joins enter the rotation directly, without sessions or lifecycle actions. Membership and catalogue identity are rechecked after asynchronous lookups; turn/speaker-only changes do not invalidate preparation. Browse references are AES-GCM authenticated/encrypted, participant/room/catalogue-connection-bound, expiring and backed by a bounded in-memory cache. They are not pending playback actions or a song queue. Strict serializers expose names/version/provider and opaque references, never raw URIs/artwork URLs, playlists, tokens or full objects. Current-turn authority is required for every play/control/reveal/finish request; joining never sends audio commands.

Catalogue identity is a separate runtime epoch, rotated only when the Music Assistant origin/token changes, the connection is forgotten, or the application restarts. Such changes discard the reader/cache and rotate reference encryption keys; returning to earlier credentials cannot revive revoked references. Speaker-only changes retain the reader/cache, browse/prepared/artwork references, and in-flight private reads. Unchanged-credential saves retain catalogue identity too. The persisted integration revision and per-process routing identity remain independent: every configuration save clears resolved playback intents and invalidates old volume revisions, but does not require a manual playback enable step. Playback lookup additionally checks the integration revision before returning; a lookup racing a destination change fails without losing the prepared choice or silently moving audio. Failed persistence rotates neither identity. No saved-file migration is required for removing the playback switch.

Artist search uses `music/search` with `media_types: ["artist"]` and remains the default; demo search remains track-only. [Multi-provider grouping](multi-provider-search.md) distinguishes verified MA identity/mapping groups from clearly labeled, unverified metadata display groups. ID-less Spotify/Tidal matches therefore share one row, but names never become canonical identity: metadata groups require an exact source before browsing and are rejected server-side for union browse/save/play. Only identity-verified artist/release groups union the listed source catalogues. Library mappings expose provider catalogue choices rather than silently limiting an artist to library albums. Album tracks use `music/albums/album_tracks` with `in_library_only: false`; the first listed source's order is retained and unmatched items follow. Source errors/coverage limits are explicit. Selecting any grouped track requires an exact source before save/play; no provider fallback is added.

Additional read-only development verification returned 20 artist results, 137 albums for a chosen provider artist, and 29 album tracks. Exact `music/item_by_uri` resolution with metadata updates disabled and the selected destination's schema-65 queue contract succeeded. Logs contained only counts/verification flags; no playback commands were issued.

## Experimental playback controller

See the [Music Assistant performance implementation](music-assistant-performance.md) for before/after measurements, event/transport behavior, deadline budgets and opt-in timing diagnostics.

The [0.3.14 backend hardening](backend-hardening.md) separates watchdog liveness from playback recovery, confirms automatic policy stops, reconciles ambiguous configuration commits, expires queued work before dispatch, and reserves connection capacity for explicit Play resolution. Settings updates subscribe to output/ownership changes independently of ordinary progress samples.

There is no host enable/disable switch or mutation endpoint. Playback availability requires a configured destination/controller, fresh inventory and queue validation, API schema 65, and no outstanding playback recovery. Persisted routing remains separate from readiness so monitoring and ownership recovery continue while the output is unavailable. Capability/volume initialization is read-only; every explicit Play validates the destination and API schema 65 before any queue mutation. The exact chosen URI is resolved and validated before queue mutation; a changed recording/version fails without a name-based substitution. `play_media` uses `option: "replace"`, exactly one URI, `radio_mode: false`, and `shuffle: false`. Autoplay/repeat/shuffle are disabled and verified. The resulting current item, one-item queue, playback state, and exact provider identity/mapping are checked before reporting playback success.

Queue observations run outside the command lane, with ownership/configuration/command-generation checks before publication; mutations remain serialized with commands/settings. Authenticated schema-65 WebSocket queue/player events wake HTTP reconciliation and confirmation, with polling as a fallback. Event payloads never establish ownership or completion themselves. Completion requires the same queue and queue-item identity, a previously observed playing state, a safe one-item queue, `state: "idle"`, and the server's `ended: true`. Upstream `player_queues/playback_tracker.py` and the deployment's generated `PlayerQueue` schema were reviewed. `fully_played` progress events are not used: upstream sets them before natural completion. App pause/stop, duplicates, unverified idle state, and lost connections do not advance. These semantics are fixture-tested; real speaker validation is pending.

External takeover invalidates metadata and releases ownership without stopping the new audio. Inactive cached queues do not confer ownership. Uncertain state fails closed and requires explicit host recovery; recovery stops only an exact still-owned item, conceals/clears app playback, and neither advances nor restarts music. Restart drops ownership without resuming/reclaiming any audio; independently running audio is left untouched, and a fresh explicit Play is required to take ownership. Stop the event before upgrades.

## Progress, artwork, and volume

The deployment's generated `PlayerQueue` schema includes `elapsed_time` and `elapsed_time_last_updated`. Only exact owned queue snapshots feed the display progress sample; short bounded extrapolation is for presentation, never completion. Public responses omit elapsed time, duration, and timestamps until reveal, sending only a fraction/status/playback ID. Unknown duration/position uses an indeterminate bar. Pause freezes progress; turn/playback changes, uncertainty, and restart clear it. A percentage can inherently reveal approximate duration through observation even without explicit times.

The public UI renders a clean idle state for absent/stopped playback, without fake song details, artwork, or progress. Playing/paused views require authoritative progress in an active session. A persistent stage carries a slow CSS glow and compact decorative activity mark; reveal updates only metadata/artwork, never their animation nodes, timing, or palette. Pause freezes those animations; reduced-motion preferences disable them. Unavailable connectivity shows an explicit unavailable state and clears stale metadata/artwork rather than implying that music stopped. This presentation changes no playback commands or completion rules.

The whole public vinyl record, including its centre text, rotates at one revolution per minute while playing. The record/sticker nodes survive reveal; upright album artwork overlays them, and missing/failed artwork leaves the same rotating record underneath. Pause freezes rotation, and reduced-motion preferences disable it. Only the unrevealed sticker replaces AOTY/SIDE A with the current public nickname and one of 180 compact, hand-written phrases; the main headline remains unchanged. A bounded local-storage shuffle bag records only phrase indexes and public identity IDs, uses all phrases before repeats, and keeps one phrase per playback across refresh/reconnect. It is display-browser-local, not server-authoritative shared history; unavailable storage falls back to memory. No song metadata, audio analysis, provider calls, or playback writes are involved.

The generated `MediaItemImage` schema supplies `proxy_id`. The upstream metadata image controller documents `/imageproxy/<64-hex-id>?size=512&fmt=png`; the app accepts only these IDs, never browser/provider-supplied URL destinations. Search/browse/resolve retain optional album and artist thumbnails. Participant image URLs use encrypted identity-bound references. Public URLs expose only playback ID/image kind after reveal; no display credential is needed, but exact reveal/identity checks run before and after I/O. There are no public artwork preloads before reveal; stale public image URLs are denied even if bytes remain cached.

Image reads use the same LAN-only DNS-pinned transport, reject redirects, cap bodies at 2 MiB and deadlines at 8 seconds, and sniff supported raster bytes (SVG/HTML are not served). Search/results, saved-list thumbnails and small artist portraits use 160px PNGs (enough for the 48px search rows at 3× pixel density); player covers use 512px PNGs. Revealed display album covers request 1024px JPEGs, rendered by the reviewed MA implementation at quality 95 to keep large covers efficient within the response/cache budgets. They are fetched eagerly only after reveal. PNG dimensions above 4096 are rejected. A 20 MiB/64-entry, five-minute server cache keys each image by size; at most 16 in-flight fetches bound resources. Browser responses remain `no-store`. Missing or rejected artwork uses a neutral record placeholder.

The 0.3.8 thumbnail optimization requested 128px, which MA rejects: its accepted sizes are `0, 80, 160, 256, 512, 1024`. The 0.3.10 correction uses 160px and normalizes legacy `?size=128` app requests to that same cached variant. The synthetic MA fixture now enforces the upstream size allowlist, including rejection of 128. Tests cover artist/album/track images, saved thumbnails, independent resolutions, and reveal-gated high-resolution display requests.

The generated commands document `players/get` (`players.read`), `players/cmd/volume_set` and `players/cmd/group_volume` (`players.control`) with integer `volume_level` in 0–100. Only the configured available destination is addressed. The controller checks volume capability/current level, chooses group semantics for groups, and revalidates configuration under its lock. Acknowledgement returns the requested level marked `pending`; a separate readback confirms or corrects it without blocking subsequent transport commands. Volume mutations require the current turn and destination revision; participant mutations additionally require the exact owned playing/paused item. The intentionally open host can adjust the configured destination even before a track starts. No volume write occurs while starting, configuring, discovering, or fetching state.

Optional volume reads run separately from queue-ownership polling, with one in-flight refresh per configuration and generation/configuration guards so slow reads cannot stall playback safety checks or overwrite newer volume changes. With a saved connection/destination, idle volume refreshes run every five seconds; active playback refreshes alongside the queue samples. Configuration changes clear stale reads/intents and refresh the new destination automatically; shutdown clears the refresh timers.

Volume confirmation starts after 300 ms; mismatches require repeated readback and a 1.2-second propagation grace period before replacing the optimistic value. No write is retried. Monotonic volume generations prevent older HTTP/SSE snapshots from undoing newer confirmed levels. Browser volume intents have a separate, latest-only request lane with a 100 ms input debounce and immediate release/keyboard commits. Private transport intents use an ordered lane and local pending projections, not the page-wide busy lock. Actor/turn/configuration changes and offline transitions drop unsent work; failed commands read state once and do not replay queued actions. Public reveals remain backend-authorized, never optimistic broadcasts.

## Indefinite pause and Music Assistant stream parking

Upstream `player_queues/controller.py::pause` starts a watcher which calls `stop` if the player remains paused for roughly 30 seconds. `resume` uses `resume_pos`/last-played position and the current queue item, so an idle stream does not necessarily mean the listener intentionally stopped the app playback. The old controller incorrectly cleared the app playback when that idle state appeared.

An already observed app-owned pause now remains paused without an expiry when its exact queue ID, queue-item ID, recording, one-item policy, and non-ended state remain intact. For idle/inactive parked queues, `players/get` must additionally report an available idle/paused destination with no foreign active source, group, or sync leader. The paused sample stays frozen. Explicit Resume verifies queue contents and confirms that the same item is playing; it never substitutes a recording or resumes automatically. Explicit Stop/Finish simply release an inactive parked selection. External source/item/group changes, real completion while playing, unverified connectivity, event end, and restart retain their fail-closed behaviour. A simulated 24-hour pause/park/resume, silent finish, and foreign-source rejection are covered by tests; an actual extended Sonos pause still requires user validation.

Read-only development verification on 2026-10-15 retrieved real artist and album PNGs (224,066 and 291,856 bytes) through the proxy, and confirmed volume support through `players/get`. No playback or volume-changing command was issued. Actual audible volume/group behaviour still needs an approved real-device test.

Read-only verification on 2026-10-15 used the configured development server (version 2.10.6/schema 65) and returned 18 available results. Output logged only counts; no credentials or track metadata. This confirms search, not live playback or complete provider coverage. Fixture tests additionally cover Spotify/Tidal/local-file results, explicit empty/error responses, privacy, and stale-request protection.

Setup checking supports authenticated schemas >=28 whose minimum supported schema is <=46. This is a read-only compatibility check, not a promise that live playback/event handling is supported. Discovery status resets after app restart; startup performs read-only inventory/queue checks and capability/volume refreshes, never audio changes. Opening or returning to host settings also requests read-only speaker discovery.

Target DNS is validated/pinned per request; only private LAN/unique-local/loopback addresses are permitted. Redirects, credentials in URLs, Ingress paths, cloud metadata/link-local/public targets, oversized bodies, and untrusted TLS certificates are rejected. Raw upstream errors/responses are not logged or forwarded. Successful inventory checking does not prove reliable natural-end detection.

## Blocking live checks

1. Read the target server’s generated API docs and record version/schema, auth, request/response shapes, and supported commands. Validate compatible capabilities; unsupported versions must fail clearly.
2. Confirm the selected Sonos speaker/group and its authoritative active queue; no broad device discovery mutations or regrouping.
3. Verify single-track playback replaces the queue, disables repeat/radio/autoplay, and cannot continue to an old queued song. This takes ownership of the configured destination and may interrupt existing audio; get approval before a live test.
4. Record actual event sequences for natural completion, stop, pause, resume, replacement, track failure, network loss, and external interference. A queue becoming idle or elapsed time reaching duration alone is **not** evidence of natural completion.
5. Map actual queue item/playback identity to the app’s playback and turn IDs. Ignore delayed, duplicated, unrelated, or recovered events. Feed only positively identified natural-end events into `Engine.complete`.
6. Reconcile live state on reconnect and restart without starting music or accidentally advancing. Mark the adapter uncertain and disable mutations when authoritative state is unavailable.
7. Conceal immediately on external track changes. Never allow an old reveal to remain attached to new metadata. Stop or safely invalidate application ownership when an external source takes over.
8. Proxy artwork using opaque application references with current-role/reveal checks; never pass administrative tokens or concealed original URLs to browsers. Bound download sizes/timeouts and prevent SSRF and caching bypasses.
9. Test privacy at the actual browser/network layer, including errors, artwork/preloads, and incoming events.

If the deployed event API cannot reliably distinguish natural completion, seek owner approval for a fallback. Do not silently implement idle-state/timer heuristics as reliable automatic turn advancement.
